## Proposed follow-up: durable native instance custody

**Proposed and unimplemented.** This appendix does not change the active reset,
runtime schema, native protocol or support metadata. The current recorded-binding
guard in [the engine](../../src/engine.zig) refuses removal when its selected
endpoint does not list a retained Codex binding. It preserves that bounded
predicate. It cannot distinguish the same native thread resumed in two processes,
remember an attachment before its first request, or prove that a fresh connection
still reaches the process previously observed. Startup configuration is not
instance ownership proof. Stock native-hook and live continuity gates remain
missing.

The smallest durable successor is a bounded native owner ledger in the same
private snapshot transaction as installation state, bindings and request
authority. Each owner records an opaque owner ID, application, existing adapter
epoch, verified process incarnation, exact native endpoint and thread attachment
generation. Ownership phases distinguish pending registration, attached, pending
detach, unresolved and detached. Paths and platform process metadata stay private;
controls receive opaque IDs and redacted state. Endpoint paths, PIDs, thread IDs,
version strings or a loaded-thread list individually cannot establish ownership.
The exact supported native hook must provide a process-incarnation nonce and
prove that its private endpoint and adapter requests belong to that instance;
platform peer/process verification requires its own version-bound evidence.
Missing proof refuses admission rather than inventing a process identity.

Persist a pending owner/thread registration **before** issuing native attachment;
activate it only after an acknowledgment matching owner, process incarnation,
epoch, thread and attachment generation. A lost acknowledgment leaves unresolved
custody. Ordinary future launches need an equivalent private registration before
entering managed mode, including threads which have never requested a credential.
Reading the installed broker configuration cannot activate that record. Late
attachment and ordinary launch must share this authority path without introducing
an Omux launcher. Older hooks report the missing capability.

[Binding identity](../../src/domain.zig) and metadata/release operations must
include the verified owner, so two processes resuming one native thread cannot
release or overwrite each other's routes. Preserve the immutable work key in
[request authority](../../src/request_authority.zig): application, native session
and request ID. Add owner identity as an immutable authorization constraint on
that intent, **not** a fresh replay namespace. Changing owner, endpoint, process,
daemon epoch or binding must never reset an accepted/uncertain work fence or its
two-attempt budget. A different owner presenting the same work is a mismatch;
registration cannot authorize accepted-stream replay or repeated tool execution.

Removal first persists an epoch-bound admission fence and stable operation ID.
That fence prevents new owners, thread attachments and leases while existing
work retains its scoped custody and terminal-report authority. Enumerate the
durable owner ledger, not only the current advertised endpoint. Every native
detach must target and acknowledge the exact owner/thread generation through a
verified instance connection. [Native probing](../../src/integrations/native_probe.zig)
must either retain that authenticated connection or reverify the same incarnation
on every connection; an endpoint replacement is a refusal. Partial detach,
unreachable owners and uncertain acknowledgments remain pending. Restore owned
configuration and retire the shared adapter epoch only after all required owner
detach acknowledgments and existing lease fences permit it. A racing new thread
cannot enter managed mode between discovery and final removal.

On daemon restart, retained attached/pending records become unverified or
unresolved until the exact instance reestablishes authority. Preserve request
history and in-flight fences; disappearance, timeout, a reused PID or an empty
socket directory cannot imply completion. A proven surviving owner can report
its existing terminal events without creating replacement work. Process-exit
retirement needs a separate explicit, evidenced rule; this proposal supplies no
automatic exit shortcut. Schema/protocol changes need an explicit migration
gate, not automatic recovery conversion. Any authorized metadata migration must
retain existing work/mutation fences and label legacy ownerless bindings
unresolved; it cannot infer owners from a current endpoint or rekey old requests
into a fresh budget. Preserve existing ciphertext and vault authority throughout.

Retired owner/thread generations leave bounded custody tombstones rejecting old
registrations, delayed detach acknowledgments and release callbacks. These are
separate from account-forget/re-enrollment tombstones and do not revoke provider
grants. Reattachment requires a new explicit generation; it never resurrects a
retired owner or erases work history. At capacity, refuse new registration rather
than evict replay or retirement authority by TTL. Safe ledger retirement remains
its existing separate design gate.

| Proposed acceptance | Meaningful required predicate |
| --- | --- |
| Duplicate native thread IDs | Two real private fixture endpoints manage the same thread ID; detaching A preserves B's binding, materialization and generation. |
| Attachment before a request | Successful and lost-reply attachment without any acquire leaves durable custody which removal must resolve, including after daemon restart. |
| Endpoint replacement | Reuse the path between list/register/detach with a different instance; refusal preserves configuration, shared capability and old custody. |
| Removal admission race | A new process or thread attempts registration after the persisted fence; no management or lease enters that epoch while existing terminal reports remain usable. |
| Crash boundaries | Interrupt before/after native acknowledgment and durable commit; restart neither forgets an owner nor claims detach from absence, and retries reconcile the same operation. |
| Owner replay and migration | Reuse accepted or uncertain work after owner/process replacement and legacy conversion; the original work fence and two-attempt budget still reject replay. Old detach/registration generations remain tombstoned. |
| Failure and capacity | Unreachable owner, unsupported peer proof, unsafe native state and full ledger produce a bounded pending/refusal outcome with custody retained. |

All fixtures, generators and checks must use declared locked Nix/Bazel actions.
Exact native-version conformance and live ordinary launch/resume/removal remain
separate gates. User impact is deliberate: affected removal can remain pending
and needs actionable repair information while Omux retains custody. Supported
idle owners can detach independently; their native stores and other owners'
authority remain intact. No routine handoff prompt, process restart, provider
access or publication is authorized by this appendix.

## Proposed follow-up: verified account metadata refresh

This appendix is proposed and unimplemented. The concrete gap is stale display
metadata: [identity enrollment](../../src/domain.zig) preserves an existing
account's `account_type`, while [import completion](../../src/engine.zig) and
[Codex usage verification](../../src/observer.zig) can receive a changed verified
`plan_type` for that same identity. A verified upgrade or downgrade therefore
does not refresh the public account type. Current routing does not use this
field; this finding does not establish incorrect entitlement admission.

Keep verified identity (provider, issuer, subject and tenant) distinct from
provider account kind, service plan and scoped entitlement observations. GitHub
account kind and Codex service plan are separate provider facts. A plan name
alone cannot authorize a model, resource, scope or API call. User labels and
active/paused/draining lifecycle remain user policy; refresh cannot overwrite
them, replace identity, remove source associations or change grant renewal
ownership. A valid downgrade is accepted under the same rules as an upgrade.
Missing evidence cannot manufacture a default/free plan.

The minimal new model is a versioned, optional `VerifiedAccountMetadata` record
keyed by opaque account ID, with separate optional account-kind and service-plan
fields. Each accepted field carries its validated provider value, evidence kind
(identity read or usage read), opaque source/grant handles and generations,
metadata revision, read admission/completion times, freshness deadline and
known/stale/unknown/ambiguous state. Retain only bounded current provenance and
pending admission authority. Unknown future provider values remain explicit
provider values without inferred entitlement. Public views expose redacted
values, freshness/state and revision; raw identity, response bodies and credential
bytes never become metadata diagnostics.

Both import identity verification and authenticated usage verification must feed
one reducer after matching the complete stored identity. Imports retain their
exact running-job, source-generation, source authorization, provider/custody
expiry and forget/re-enrollment fences. Usage reads capture exact account
incarnation, grant generation, source authority and metadata admission revision
before provider I/O, then recheck them at completion. A detached source can still
support a read through an independently valid authorized grant; disconnected,
expired or superseded authority cannot. Forget removes the metadata and retires
its incarnation. Re-enrollment creates new authority which delayed old reads
cannot update. Metadata refresh never enrolls an identity or revives a grant.

Persist read admission and revisions before issuing new metadata-bearing reads.
Serialize refresh for a known account. Imports whose identity is not yet known
retain their admission interval until verification identifies the account.
Apply a revision check at commit: an obsolete response cannot replace a newer
accepted fact. When overlapping reads disagree without a provider revision
whose ordering is verified for both endpoints, mark the field ambiguous rather
than choosing by completion order, local request order or a provider timestamp.
A subsequent non-overlapping verified read can resolve that ambiguity. Freshness
is bounded by the read's admission time, a declared maximum age and any applicable
evidence/authority deadline; delayed completion does not extend it. Failed,
malformed, mismatched or stale reads preserve retained history with honest
freshness/state. Absence of quota rows must not suppress an otherwise valid plan
fact, and absence of a plan must not infer one. Commit accepted metadata with
related quota/grant changes atomically; rollback restores revisions as well as
facts. Restart retires incomplete read admissions without adopting orphan
completions or resetting accepted revisions. Snapshot, health and export remain
observation-only.

Introduce an explicit persisted schema/API version and migration gate. Existing
`account_type` becomes legacy display history, not retroactively verified fresh
metadata; new verified fields begin unknown until a valid read. Migration must
preserve identities, user labels, lifecycle, independently valid grants,
ciphertext generations, vault authority, forget tombstones and request/mutation
fences. Unsupported or failed conversion refuses before changing custody.
Versioned public metadata fields must make legacy/fresh/ambiguous distinctions
visible; silently changing the meaning of the existing string is insufficient.

| Proposed acceptance | Meaningful required predicate |
| --- | --- |
| Upgrade and downgrade | Actual held import and usage verification paths accept free-to-paid-to-free evidence for one unchanged identity, including unchanged credentials; user label, lifecycle, source associations and independent grants remain intact. |
| Ordering and freshness | Deliver old reads after newer reads, overlap conflicting source reads, and cross freshness deadlines; old data cannot overwrite fresh facts, conflict remains ambiguous, and failure never guesses a free plan. |
| Lifecycle authority | Rotate/cancel an import or grant, disconnect a source, and forget/re-enroll while reads are held; retired completions cannot mutate metadata. A valid detached-source grant still refreshes without restoring source attachment. |
| Evidence boundaries | Wrong subject/tenant, malformed response, missing quota, missing plan and supported unknown provider values exercise the shared reducer; plan-only evidence never creates entitlement, call authorization or renewal ownership. |
| Persistence and public view | Restart and interrupt migration/commit around admission and acceptance; preserve metadata revisions, tombstones, ciphertext and work fences, with redacted versioned views distinguishing stale, unknown and ambiguous facts. |

These are future declared locked Nix/Bazel fixture gates, not completed tests.
Provider endpoint semantics and exact supported versions require their own
evidence; this proposal authorizes no provider access and establishes no live
account-refresh or continuity claim.

## Proposed foundation: whole-snapshot admission before effects

This contract was proposed and unimplemented at the saved evening checkpoint.
The [active admission sprint](omux-native-admission-sprint-2026-10-04.md) now
implements and verifies it; current gates remain in that sprint's evidence.
It precedes additional durable
native owner records because those records also need reserved persistence space.
[Engine persistence](../../src/engine.zig) serializes the complete private metadata
snapshot, and [storage](../../src/storage.zig) checks its 16 MiB bound at commit.
The existing 4 MiB request and 6 MiB mutation reservations cover their respective
sections; domain state, source descriptions, installed integrations, generations
and future custody records had no shared before-effect reservation in that source
epoch. A persisted
started intent can fit while its later metadata growth cannot. Existing poisoning
and indeterminate fences remain necessary; section bounds do not prove a complete
snapshot guarantee.

Use one actor-owned whole-envelope budget. A bounded counting writer using the
actual locked serializer measures current non-ledger bytes and envelope overhead.
Add the existing worst-case ledger reservations and durable per-effect future
growth credits. Their sum must remain at or below the storage bound. Every writer,
including background import, observation, renewal and recovery paths, respects
outstanding credits; a new unrelated operation cannot consume completion space
already promised to accepted work.

Each operation needs a bounded outcome plan before admission. Local atomic changes
prepare and measure their complete candidate snapshot before the SQLite transaction.
External operations reserve possible domain, metadata and failure/indeterminate
growth, then persist those credits with their original authority before issuing
provider I/O, native RPCs or configuration changes. Credits survive restart and
uncertainty. Release unused capacity only with a committed terminal outcome or
fenced cancellation that prevents every later completion from mutating state.
Owner, process or adapter replacement cannot create a new replay key, restore
attempt budget or release uncertain credits.

Result capacity is an independent admission predicate. Native installation/removal
currently returns a configuration path, while mutation results have a 1 KiB cached
result limit. Bound or measure the encoded redacted result before changing native
configuration, and apply the same rule to variable native thread lists. Provider
response plans require declared cardinality and encoded-size bounds before the
effect. Missing bounds refuse admission. Oversized output after an external effect
remains indeterminate or quarantined; it cannot silently discard custody, retry
the effect or increase the storage limit.

Byte credits do not guarantee allocation, disk, entropy, vault or transaction
success. Preserve ciphertext-before-write, storage poisoning, refresh single-writer
authority, forget generations and started/indeterminate work fences. Existing
snapshots whose future obligations exceed the new budget require an explicit
repair/migration gate preserving all authority. No TTL eviction, automatic rekeying
or plaintext fallback makes an overcommitted snapshot admissible.

| Proposed acceptance | Meaningful required predicate |
| --- | --- |
| Native installation/removal | Actual configuration path or thread-list result overflow and insufficient whole-envelope space refuse before configuration, capability or native detach changes. |
| Held credential import | Reserve verified enrollment growth before I/O; unrelated mutations cannot consume it, and authorized completion still atomically commits encrypted custody. |
| Adapter acquire/report | Reserve binding, lease and report growth before returning a handle; accepted work can terminate under saturation without another attempt or replay allowance. |
| Account forget | Multi-source tombstone expansion commits with ciphertext deletion or refuses atomically with old grants and tombstones intact. |
| External-effect crash/restart | Credits and original intent survive the effect/completion gap; restart preserves indeterminate authority and duplicates never repeat the effect. |

These future gates must exercise the real engine/storage and private native/import
paths through locked Nix/Bazel. They are not tests completed by the current byte
partitions, actual oversized SQLite completion refusal or installed Sting proof.
